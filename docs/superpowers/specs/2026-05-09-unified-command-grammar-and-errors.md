# Unified Command Grammar & Structured Errors

**Status:** Draft — pending user approval
**Date:** 2026-05-09
**Author:** Claude (with linyilun)
**Replaces:** Task #220 (structured-errors only)

---

## 1. Why now

Three drift events in the last 30 days exposed a single root cause:

1. **Doctor hardcoded grammar drift** (PR #285, today). `next_steps_text/5` rendered
   `esr --env=dev feishu bind ...` long after the grammar refresh deleted that form.
   No CI failed. Operators got bad copy-paste.
2. **`/help` data-driven, but ad-hoc help bodies are hand-written.** The slash
   reference is generated from `slash-routes.default.yaml`, but every command
   module hand-writes its own usage strings inside its error returns. Diverges
   silently.
3. **`/workspace` (bare prefix) returns nothing useful** — the operator must
   already know `workspace:new` exists. There's no module-level help affordance.

Every one of these is a class of bug, not an instance. The fix is to make the
grammar one piece of data with multiple presenters — and to delete the parallel
hand-written copy.

The same problem applies to **error responses**: every command writes its own
`%{"type" => "...", "message" => "..."}` map, with the message often duplicating
or contradicting the public docs. Task #220 already called this out. Doing both
in one spec means we touch every command module exactly once.

---

## 2. Goals

A command's identity, signature, help text, and error vocabulary are declared
**once** in the command module via a structured DSL. From that single source we
generate:

- Slash routing (`/<resource>:<method> ...`)
- CLI dispatch (`esr exec <kind> --key=value`)
- HTTP/URI shape (`POST /api/exec/<kind>` body `{args: ...}`)
- Help rendering (`/help`, `/<resource>`, `/<resource>:help`)
- Operator-facing reference doc (`docs/grammar/commands.md`)
- A typed error catalog (`docs/grammar/errors.md`) with stable `type` codes
- Compile-time enforcement that drift cannot land

Bare-prefix help (`/workspace` → list of methods, `/<unknown>` → list of resources)
ships in the same migration so operators can discover commands without reading
the help file.

### Non-goals

- We do **not** add a runtime DSL that lets plugins ship custom grammar at boot
  time. (Plugin-scoped command registration is already covered by the
  2026-05-08 plugin-command-registration spec; this spec consumes that surface,
  doesn't replace it.)
- We do **not** change the wire format of slash invocations or admin-queue
  payloads. The `kind` strings, the slash texts, the args keys are already
  consumed by FAA + CLI + HTTP — backward compatibility is mandatory.
- We do **not** introduce localization for help/error text in this spec.
  Strings stay zh_cn-with-en-fallback as today; localization is a separate
  followup.

---

## 3. Three design decisions (already approved)

User confirmed in chat 2026-05-09:

| #  | Question                                                 | Choice                                                                     |
| -- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| Q1 | Where does the canonical grammar live?                   | **B** — module-attribute macros inside each `Esr.Commands.*` module        |
| Q2 | How do commands render their help / error text?          | **C** — each module exposes a `command_meta/0` callback the renderer reads |
| Q3 | What happens when slash-routes.yaml diverges from a module? | **A** — compile-time hard error; the build fails                           |

These choices push every authoring affordance to the module itself and make
`slash-routes.default.yaml` derived state, not source. The yaml stays as a
read-time artifact (FAA + Adapter routes load it) but is regenerated by
`mix esr.gen_slash_routes` from `command_meta/0` and gate-checked in CI.

## 4. The four pillars

### Pillar 1: `command_meta/0` callback (Q1+Q2 in code)

Every command module implements:

```elixir
defmodule Esr.Commands.Workspace.New do
  use Esr.Commands.Meta

  command :workspace_new do
    slash         "/workspace:new"
    category      "Workspace"
    description   "创建新 workspace。folder=<path> → repo-bound；不传 → ESR-bound"
    permission    "workspace.create"
    requires_user_binding      true
    requires_workspace_binding false

    arg :name,      required: true,  doc: "workspace 名（ASCII alnum + - + _）"
    arg :folder,    required: false, doc: "绝对路径，必须是 git repo（repo-bound 模式）"
    arg :transient, required: false, default: "false", doc: "true 时 ESR-bound 临时 ws"
    arg :owner,     required: false, doc: "默认取 args.username"

    error :invalid_name,                "workspace 名必须匹配 ^[A-Za-z0-9][A-Za-z0-9_\\-]*$"
    error :unknown_owner,               "owner 未在 users.yaml 注册；先跑 user_add"
    error :folder_not_dir
    error :folder_not_git_repo
    error :transient_repo_bound_forbidden
    error :name_exists
    error :registry_put_failed
  end

  @behaviour Esr.Role.Control
  # ... execute/1 unchanged ...
end
```

The `use Esr.Commands.Meta` import:

- Injects an `@behaviour Esr.Commands.Meta`.
- Adds `command_meta/0` returning a struct (`%Esr.Commands.Meta.Spec{}`) populated
  at compile time from the DSL block.
- Validates the DSL at compile time: kind must be a snake_case atom; slash must
  match the kind (or be `:none` for internal-only kinds); args must be a list
  of `%Arg{}`; errors must be unique.
- Registers the module into a compile-time module manifest used by gen-yaml +
  doc generation.

The DSL is intentionally a thin sugar layer. Behind the scenes it expands to a
single `def command_meta, do: %Spec{...}` clause and a few `@spec_*` module
attributes the macros use during compilation.

### Pillar 2: Generated `slash-routes.default.yaml` (Q3)

`runtime/priv/slash-routes.default.yaml` becomes derived state:

- `mix esr.gen_slash_routes` walks every `Esr.Commands.*` module that
  `command_meta/0`s, emits the yaml deterministically (sorted by kind).
- `mix esr.check_command_docs` (the CI gate) regenerates in-memory and
  diffs against the file on disk. Any divergence is an error and fails CI.
- The current file stays at its current path (FAA, Adapter, and tests load
  it by path; we don't move it). Operators who edit it by hand get a CI
  failure with a clear "run `mix esr.gen_slash_routes`" message.

There's still an `internal_kinds:` section for kinds that have no slash form
(`user_add`, `feishu_bind`, `register_adapter`, etc.). The DSL marks these
with `slash :none` and they emit into that section.

### Pillar 3: Per-module help/error renderers (Q2 in practice)

The `Esr.Commands.Render` module is the single renderer. It takes a
`%Spec{}` and emits:

- `Render.help_line/1` — single line for `/help` (slash + args + description)
- `Render.module_help/1` — multi-line for `/workspace` / `/<resource>:help`
- `Render.error/2` — given a kind + error code, returns `%{"type" => ..., "message" => ...}`
  with the message body coming from the spec's `error/2` declaration

`Esr.Commands.Help` (the `/help` command), `Esr.Commands.Doctor`, and the
new `Esr.Commands.ResourceHelp` (handles `/workspace`, `/session`, etc.)
all delegate into `Render`. No command module hand-writes its `/help` line
or its bootstrap-error copy ever again.

The error path is the bigger win. Today every module returns:

```elixir
{:error, %{"type" => "invalid_args", "message" => "workspace_new requires args.name"}}
```

After this spec lands, the module returns:

```elixir
Render.error(:workspace_new, :invalid_args, %{detail: "args.name missing"})
```

The renderer fills in the canonical message from the `error :invalid_args, "..."`
declaration, optionally interpolating `detail`. The error type code and the
operator-facing copy live in one place; both are visible to the doc generator.

### Pillar 4: Bare-prefix help routing (UX)

The slash router (`Esr.Entity.SlashHandler` + `Esr.Resource.SlashRoute.Registry`)
gains three new behaviors:

| Input                         | Behavior                                                                    |
| ----------------------------- | --------------------------------------------------------------------------- |
| `/`                           | List resources (`workspace`, `session`, `agent`, ...) — short list          |
| `/workspace`                  | List `workspace:*` methods + one-line each (built from `command_meta/0`)    |
| `/workspace:help`             | Same content as `/workspace` (explicit alias for discoverability)           |
| `/<unknown>`                  | Friendly error + list of valid top-level resources                          |
| `/workspace:<unknown>`        | Friendly error + list of methods under `workspace`                          |
| `/workspace:new <bad args>`   | Renderer-formatted error (Pillar 3), unchanged from today's behavior        |

Implementation: when `Registry.lookup/1` returns `:not_found`, the SlashHandler
falls into a new `Registry.lookup_prefix/1` — if the input matches a known
resource prefix, it dispatches to `Esr.Commands.ResourceHelp.execute(%{"args" => %{"resource" => "workspace"}})`.
That command queries the registry for all routes whose kind starts with
`workspace_*` and renders the module help. Same path serves the explicit
`/<resource>:help` form.

## 5. Doc generation (`docs/grammar/`)

`mix esr.gen_command_docs` writes two operator-facing files:

- `docs/grammar/commands.md` — every command, grouped by category, slash + CLI
  forms, args, description, error vocabulary. Sorted deterministically.
- `docs/grammar/errors.md` — flat catalog of `type` codes, which kinds emit
  them, the canonical message. Useful for adapter authors building structured
  notification surfaces (Pillar 4 of task #220's original ask).

Both files live in `docs/grammar/` (new directory) and are committed. CI
regenerates and diffs them just like the yaml.

**Generated-file header.** Every generated file (the two docs above + the
regenerated `slash-routes.default.yaml`) starts with a banner that flags it
as machine-output and points at the source:

```
<!-- AUTOGENERATED — DO NOT EDIT BY HAND.
     Source: command_meta/0 in each Esr.Commands.* module.
     Regenerate: mix esr.gen_command_docs (or mix esr.gen_slash_routes).
     Drift in this file fails CI via mix esr.check_command_docs. -->
```

The yaml uses `#`-comment form. The CI gate strips both forms before diffing
so banner edits don't masquerade as content changes — but a missing banner
is itself a CI failure (check_command_docs verifies it on every regenerated
file).

---

## 6. CI gate: `mix esr.check_command_docs`

A single mix task wraps three checks:

```bash
mix esr.check_command_docs
# 1. Walk every Esr.Commands.* module, ensure command_meta/0 exists.
# 2. Generate slash-routes.default.yaml in memory; diff against on-disk copy.
# 3. Generate docs/grammar/{commands,errors}.md; diff against on-disk copies.
# Any non-zero diff → exit 1 with a helpful message.
```

Wired into `.github/workflows/ci.yml` as a separate step so a failure points
the operator at the right command (`mix esr.gen_slash_routes &&
mix esr.gen_command_docs`).

## 7. Migration: one shot, ~74 modules

Per user direction: not gradual.

Module count, verified 2026-05-09: 74 `.ex` files under
`runtime/lib/esr/commands/` (core) + 4 under `runtime/lib/esr/plugins/*/commands/`
(plugin command modules). Plugin modules are converted in the same migration
because their wire shape is identical and skipping them would leave the
manifest incomplete.

The migration converts every existing command module in a single PR (or a
small handful of stacked PRs to keep diffs reviewable). The order:

1. **Phase 1 — DSL infrastructure.** `Esr.Commands.Meta` module + `Spec` struct
   + macro implementation + `Esr.Commands.Render` + `Esr.Commands.ResourceHelp`.
   No command modules touched yet; only new code added.

   Phase 1 also adds two prerequisites the spec previously assumed:

   - **Add `Ymlr` to deps.** `runtime/mix.exs` today only carries
     `{:yaml_elixir, "~> 2.11"}` which is a parser, not an emitter. The gen task
     needs a deterministic emitter. Pull in `{:ymlr, "~> 5.0"}` (sorts keys,
     stable line endings).
   - **Formalize `Esr.Role.Control` callback.** Today `execute/1` is a
     convention every command module follows but `Esr.Role.Control` only
     declares `__role__/0`. Add `@callback execute(map()) :: {:ok, map()} | {:error, map()}`.
     This is a one-line behaviour change but it makes Phase 2's "the DSL plugs
     into the existing contract" claim literally true rather than merely
     conventional.

2. **Phase 2 — One canary module.** Convert `Esr.Commands.Workspace.New` to
   the DSL. Verify yaml regeneration is byte-identical to current
   `slash-routes.default.yaml` for that one entry. Verify error returns are
   identical (test with snapshot-of-current-error-shape).
3. **Phase 3 — Bulk conversion.** Remaining ~73 core modules + 4 plugin
   modules. Each conversion is mechanical: extract the existing yaml row +
   existing error returns into the DSL, delete the now-redundant hand-written
   strings.
4. **Phase 4 — yaml + docs become derived.** Replace the hand-edited
   `slash-routes.default.yaml` with one generated by `mix esr.gen_slash_routes`.
   First run lands a no-op diff (because Phase 2 + 3 made them byte-identical).
   Add `docs/grammar/commands.md` + `docs/grammar/errors.md`.
5. **Phase 5 — CI gate.** Add `mix esr.check_command_docs` to CI as a
   blocking step. Today the only workflow file is
   `.github/workflows/enforce-pr-from-dev.yml` (PR base-branch check, not
   build/test). Phase 5 **creates** `.github/workflows/ci.yml` from scratch
   with at minimum: `mix deps.get`, `mix compile --warnings-as-errors`,
   `mix esr.check_command_docs`, `mix test`. The check_command_docs step
   gets its own line so a drift failure points at the right command.
6. **Phase 6 — Bare-prefix routing.** Wire `/workspace`, `/<resource>:help`,
   `/<unknown>` paths into SlashHandler. Add e2e scenario that posts
   `/workspace` in chat and asserts the response lists workspace methods.

Phase 5 is the gate. Once it lands, every future command module gets the DSL
or the build breaks.

## 8. What stays the same

- The `Esr.Role.Control` behaviour (`execute/1` callback) is unchanged. The
  DSL is metadata; the execution path is still the function clause stack each
  module owns today.
- `slash-routes.default.yaml` keeps its current schema (`schema_version: 1`).
  Only the **author** changes (humans → mix task).
- The CLI entry point (`runtime/lib/esr/cli/main.ex`) keeps its current shape:
  `esr exec <kind> --key=value` resolves through the same kind→module map.
- FAA / Telegram / future adapters keep their current loader path. They read
  the yaml; they never call `command_meta/0` directly. (This boundary keeps
  adapters dumb: they're still just yaml consumers.)

---

## 9. What this enables next

- **Plugin-scoped commands** (2026-05-08 spec) plug into the same `Spec`
  struct. A plugin's command_meta/0 lives inside the plugin module; the gen-yaml
  + gen-docs tasks discover it via the plugin manifest.
- **Localization.** Once help/error text is data, swapping in a translation
  table is a renderer concern, not a per-module rewrite.
- **Adapter notification surfaces** can render structured errors with stable
  `type` codes. The Telegram adapter, when we ship it, gets the same error
  vocabulary as Feishu without code duplication.
- **Schema export.** A future `GET /api/grammar/commands.json` endpoint can
  return the manifest as JSON for tooling (autocompletion, IDE plugins, the
  upcoming web TUI command palette).

## 10. Risks & open questions

### Risk: macro complexity

The DSL must be readable. If the macro is too clever, future authors will
copy-paste-debug it for hours. Mitigation: keep the macro thin (one block,
one struct output, no AST manipulation beyond unquoting). If the implementer
finds the macro growing teeth, fall back to a plain map literal — the win is
the single source of truth, not the syntax sugar.

### Risk: byte-identical yaml regeneration

Phase 2's "verify byte-identical" gate is non-trivial because Elixir map
serialization order isn't yaml-stable. Mitigation: emit yaml via a
deterministic emitter (`Ymlr`, added to deps in Phase 1), freeze the ordering
rule in the gen task itself. Phase 4's first run almost certainly produces a
non-empty diff against the current hand-edited file (whitespace, comment
preservation, key order). The Phase 4 PR therefore has two commits: one that
re-emits the current yaml under the new emitter (establishes baseline, no
semantic change), one that wires `mix esr.gen_slash_routes` as the author. The
canary in Phase 2 only verifies semantic identity (parsed yaml → same map),
not byte identity, to keep that work isolated to Phase 4.

### Risk: error code churn

Today's error `type` strings (`invalid_args`, `unknown_workspace`, etc.) are
already de-facto stable — adapters key off them. The DSL **must not** silently
rename any. Mitigation: Phase 2's canary verifies the error map shape is
identical. If a renamer is wanted, it's a separate followup PR with a
deprecation note.

### Risk: bare-prefix routing breaks adapters

FAA today happily rejects unknown slashes with the deprecated-slash hint. The
new `/<resource>` and `/<resource>:help` paths must not conflict. Mitigation:
the deprecated-slash table (`@deprecated_slashes` in SlashHandler) takes
priority over the new prefix routing — if someone types `/new-workspace`
(removed), they still get the migration hint, not the workspace help.

### Plugin command discovery

The DSL must reach both `Esr.Commands.*` (core) and `Esr.Plugins.*.Commands.*`
(in-tree plugins like `claude_code` and `feishu`). Today's plugin command
modules live at `runtime/lib/esr/plugins/{claude_code,feishu}/commands/*.ex`
and use the same `@behaviour Esr.Role.Control` + `execute/1` convention as
core. The 2026-05-08 plugin-command-registration spec defines a plugin
manifest where each plugin exposes a `command_modules/0` list of its command
module names.

Resolution: `mix esr.gen_slash_routes` walks `Esr.Commands.*` for core, then
calls each enabled plugin's `command_modules/0` and walks those too. CI only
checks core + plugins included in the default plugin manifest. Out-of-tree
plugins are responsible for running the check themselves.

A consequence worth flagging: plugin command modules adopting the DSL pulls
the 2026-05-08 plugin-command-registration spec onto this spec's critical
path. If that spec hasn't merged its `command_modules/0` manifest hook, this
spec falls back to a module-name allowlist for in-tree plugins
(`Esr.Plugins.ClaudeCode.Commands.*`, `Esr.Plugins.Feishu.Commands.*`) until
the manifest lands.

## 11. Acceptance criteria

The migration is "done" when:

- [ ] Every `Esr.Commands.*` module exposes `command_meta/0` (compile-time
      enforced via behaviour).
- [ ] `slash-routes.default.yaml` is regenerated by `mix esr.gen_slash_routes`
      and byte-identical to the previous hand-edited copy on first run.
- [ ] `docs/grammar/commands.md` + `docs/grammar/errors.md` exist and are
      committed.
- [ ] `mix esr.check_command_docs` is a blocking CI step.
- [ ] Posting `/workspace` (no method) in chat returns a list of
      `workspace:*` methods. (e2e scenario, asserted.)
- [ ] Posting `/<unknown>` returns a friendly error listing valid resources.
- [ ] Editing a command module's DSL without re-running `mix esr.gen_slash_routes`
      causes CI to fail with a clear "regenerate the yaml" message.
- [ ] No command module hand-writes a `/help` line or a `%{"type" => ..., "message" => ...}`
      string in its error returns. All go through `Esr.Commands.Render`.
